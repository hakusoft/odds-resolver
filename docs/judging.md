# 判定の作法

仮説を前向きログで検証するときの手順。#106 / #148 / #56 / #169 で踏んだ穴を
並べ、**基準を固定する前**と**判定するとき**に確かめることをまとめる。

作法は人の善意と記憶に依存する。**コードで守れるものはコードに移してある**
（下の表の「仕組み」列）。残りはこのチェックリストで確かめる。

## 基準を固定する前

| # | 確かめること | 踏んだ穴 | 仕組み |
|---|---|---|---|
| 1 | **測定と記録が同じ入力・同じ計算か。** 閾値を引いた分布と、実際に記録する値を同じレースで突き合わせ、一致を確かめる | #169: 分布は T-2、記録は T-15 前後の単勝で計算していた | 無し（突き合わせは手で行い、PR に件数を書く） |
| 2 | **検出力を見積もったか。** `ingest.tools.power` で期待的中数・区間幅・偽陽性率を出し、issue に貼る | #56: n=300 で期待的中 0.8 件。1 件の当落で 0% と 107% の二択になった | `ingest/tools/power.py` |
| 3 | **基準に有意性の裏付けがあるか。** 「3 ポイント」のような差の基準は、その n で偶然に出る幅と比べる | #148: 超過したのは n が最も薄い 2 帯だった | 2 と同じ |
| 4 | **基準を git に置いたか。** 判定ツールを n=0 のうちに置き、基準を定数とテストで固定する | — | `judge_*.py` の定数とテスト |

### 検出力の見積もり方

```bash
python -m ingest.tools.power --hit-rate 0.0204 --n 300 500 --min-hits 10
```

- `--hit-rate` は**結果を含まない材料**から取る（理論確率の平均など）。
  判定前のログで的中率を数えると、回収率も見えてしまう（#170）
- 出る区間は的中数の揺れだけを見た**下限**。オッズのばらつきの分、実際はもっと広い
- 偽陽性率は「真の回収率が 80%（控除率 20%）なのに 100% を超えて見える確率」。
  これが高い n で「効果あり」が出ても、結論としては弱い

## 判定するとき

| # | 確かめること | 踏んだ穴 | 仕組み |
|---|---|---|---|
| 5 | **判定は 1 回だけ。** 2 回目は計算せず、保存済みの結果を返す | — | `judgments/exotic_edge/{kind}.json` への条件付き書き込み（#171） |
| 6 | **判定前に率を見ていないか。** 見たなら判定時に申告する | #170: 調査中に回収率 128.8% を見た | `--check` と morning-check は率を出さない |
| 7 | **結果が弱いなら弱いと書く。** 基準は動かさず、但し書きを添える | #56: 「効果あり」が 5 日で 49% に落ちた | 無し |
| 8 | **判定後に掘らない。** 「全体でダメだったからオッズ帯別で」は禁止 | — | 5 と同じ（再判定できない） |

## 判定の記録

`judge_exotic_edge` は判定結果を S3 の `judgments/exotic_edge/{kind}.json` に
書いてから表示する。書けなければ表示しない（記録の無い判定を見ると、もう 1 回
打ててしまうため）。

`judgments/` ができる前に判定した馬単（2026-09-30）は、S3 に遡って書かずに
`PRIOR_JUDGMENTS` としてコードに固定してある。

judgments/ ができる前に判定した #106 / #148 は、それぞれの judge ツールに記録を
足していない。再判定を防ぐ仕組みが要るなら同じ形で足せる。
